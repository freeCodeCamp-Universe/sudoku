# Lesson authoring reference

Rules and conventions for writing lesson files. For how lessons are loaded, built, and rendered, see [`architecture.md`](architecture.md#learn-layer).

## Lesson file structure

Each lesson is `src/curriculum/lessons/<NNN>.md`. The number is a grouping convenience: module 1 uses `101.md` to `199.md`, module 2 uses `201.md` to `299.md`. `src/curriculum/ordering.ts` decides the real order. The loader ignores any file not listed there.

```ts
export const curriculum: readonly OrderingModule[] = [
  {
    module: 1,
    slug: 'getting-started',
    title: 'Getting Started',
    lessons: ['101.md', '102.md', '103.md', '104.md'],
  },
];
```

A lesson entry is a filename, or `{ file: '105.md', wip: true }` to hide one lesson. Set `wip: true` on a module to hide the whole module. Hidden lessons appear only in development with `SHOW_UPCOMING_LESSONS=true`.

**Scaffolding**

```bash
pnpm add-module --number=2 --slug=techniques --title="Techniques"
pnpm add-lesson --module=2 --title="Candidate notes"
pnpm add-lesson --module=2 --title="Candidate notes" --type=practice --after=201.md
```

`add-module` creates an intro and a review lesson, and places the module with `--before=<module>` or `--after=<module>`, or at the end. `add-lesson` takes the next free number in the module's range, marks the entry `wip: true`, and inserts it before the review lesson or where `--before=<file>` or `--after=<file>` says. Run either script with no arguments to be prompted for its values.

**Frontmatter**

| Field        | Notes                                                                                                                |
| ------------ | -------------------------------------------------------------------------------------------------------------------- |
| `id`         | Required. 24 hex characters, unique across the curriculum. Generated by the scaffolding scripts; never hand-edited.  |
| `title`      | Required. Rendered as the page's `<h1>` and in the curriculum tree. Renders inline markdown such as backticks.       |
| `type`       | `intro`, `learn`, `practice`, or `review`. Defaults to `learn`. Changes grouping and wording only, never validation. |
| `layoutType` | `article` or `interactive`. The loader decides the real layout from the sections present. See Layout below.          |

**Section markers**

| Marker               | Purpose                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `# --instructions--` | Markdown shown to the learner.                                                             |
| `# --files--`        | Seed files for the interactive panel: one `## <filename>` heading and code fence per file. |
| `# --config--`       | A `json` code block. See [Config block](#config-block).                                    |
| `# --author-notes--` | Notes for authors and reviewers. Never rendered.                                           |

Any other `# --name--` marker fails the build.

**Layout**

A lesson is **interactive** when it has a `# --config--` section, or when it declares `layoutType: interactive` and has a `# --files--` section. An interactive lesson shows the instructions beside the interactive panel. Every other lesson is an **article**, a centered prose column with an outline built from its H2 and H3 headings.

## Instructions

Instructions are GitHub-flavored markdown. `renderMarkdown` in `src/learn/Markdown/renderMarkdown.ts` turns them into HTML at build time.

- Do not write an H1. The title is the page's only H1. Start sections at `##`.
- H2 and H3 headings get slug IDs, so `## Seeing a cell's houses` becomes `id="seeing-a-cells-houses"`. The article outline links to them.
- Links open in a new tab with `rel="nofollow noopener noreferrer"`.
- The renderer wraps tables so they scroll horizontally on narrow screens.

### Showing the copy button on a code fence

Code fences have no copy button by default. Add `copy` to the info string to show one:

````markdown
```ts copy
const peers = 20;
```
````

`copy` works without a language too: ` ``` copy `. `no-copy` is accepted and does nothing.

### Tab groups

Article lessons can embed tabbed code viewers with `:::tabs` / `:::` regions. Interactive lessons do not render them.

````markdown
:::tabs

### row.txt

```txt
5 3 . . 7 . . . .
```

### column.txt

```txt
5
6
.
```

:::
````

- Each heading names a tab. Any level from `#` to `######` works, because the parser reads it as a tab label, not a document heading.
- Each heading must be followed by a code fence. The language tag is optional.
- A group needs at least one tab and must be closed with `:::` on its own line.

The loader parses these regions in `src/curriculum/tabBlocks.ts`. The `TabGroup` component in `src/learn/TabGroup/TabGroup.tsx` renders them with arrow-key, Home, and End navigation.

### Raw HTML

Instructions accept raw HTML from the [`sanitize-html` default allowlist](https://github.com/apostrophecms/sanitize-html#default-options), which covers tags like `kbd`, `figure`, `figcaption`, and `table`, plus `<img>`. Anything else fails the build, including `<canvas>`, event handler attributes, and `javascript:` URLs. The check skips inline code and code fences, so you can show HTML as an example.

| Tag     | Allowed attributes                                            |
| ------- | ------------------------------------------------------------- |
| `<img>` | `src`, `srcset`, `alt`, `title`, `width`, `height`, `loading` |

The allowlist is `LESSON_HTML_OPTIONS` in `src/curriculum/sanitize.ts`.

## Images

Use Markdown image syntax, `![description](/images/learn/<file>)`, rather than writing an `<img>` tag. The description becomes the image's `alt` text; use `![](...)` when the image is decorative or its meaning is already in the text.

- Put local images in `public/images/learn/` and reference them from the site root, as `/images/learn/<file>`.
- Remote images must use `https`. They add a third-party request for every learner and can change or disappear, so prefer local files for anything the lesson depends on.
- Images shrink to fit narrow columns and keep their aspect ratio. Markdown image syntax does not set `width` or `height`.
- Text inside an image is invisible to screen readers. Put anything the learner must read into the `alt` or the prose.

## Config block

The `# --config--` section holds one code fence labeled `json`. Any other label, including `jsonc`, fails the build. `parseJsonWithComments` in `src/curriculum/jsonWithComments.ts` strips `//` and `/* */` comments, then parses the rest as strict JSON, so trailing commas still fail.

````markdown
# --config--

```json
{
  // Each checklist item is a requirement the learner must meet.
  "checklist": [
    {
      "label": "See the three kinds of house",
      "hint": "You can find a row, a column, and a box shaded in the diagram.",
      /* Graded by the panel's LessonEngine. */
      "test": { "placeholder": true }
    }
  ]
}
```
````

| Property    | Notes                                                                                |
| ----------- | ------------------------------------------------------------------------------------ |
| `checklist` | Array of checklist items. See [Checklist items](#checklist-items). Defaults to `[]`. |
| `board`     | Optional playable board. See [Board config](#board-config).                          |

### Board config

A `board` object gives the lesson a playable puzzle. The panel shows the board beside the Normal/Candidate input tabs, with no game toolbar.

Cell ids use the 1-based rc notation learners see, so `"r1c1"` is the top-left cell. The loader converts them to the engine's 0-based ids. Never write engine ids (`r0c0`) in a lesson: they parse, but grade the wrong cell.

```json
{
  "board": {
    "variant": "mini",
    "givens": { "r1c1": 1, "r2c3": 1 },
    // every cell on the board
    "solution": { "r1c1": 1, "r1c2": 2, "r1c3": 3, "r1c4": 4 },
    "cellSelection": "multiple",
    "highlights": { "sameValue": false }
  }
}
```

| Field           | Notes                                                                                                                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `variant`       | Required. A registered variant id.                                                                                                                                                                            |
| `givens`        | Required. The prefilled cells only. Each must match `solution`.                                                                                                                                               |
| `solution`      | Required. Every cell on the board, with no conflicts under the variant's rules.                                                                                                                               |
| `cellSelection` | `"single"` (default) or `"multiple"`. Use `"multiple"` when the learner must select a set of cells. Selected cells then show a background fill and check mark, and the blue ring marks only the focused cell. |
| `highlights`    | Booleans for `peers`, `sameValue`, and `conflicts`. Each defaults to `true`. `conflicts: false` also drops "in conflict" from the spoken cell label.                                                          |

Values must be symbols of the variant. Any other field fails the build.

Variants with a `deriveStructure` or `deriveGutters` hook (killer, jigsaw, arrow, and others) are not supported yet, because the config can't pin their cages, regions, or clues. The loader rejects them, and it rejects a `structure` field. Don't invent a `structure` shape from the variant's engine or overlay types.

## Checklist items

Structure: `{ "label": "...", "hint": "...", "test": { ... } }`. `hint` is optional.

Learners don't see the checklist. Each item is a requirement, and the Next button appears once every requirement passes. Because learners don't see the list, the instructions must say what to do.

- **`label`** names the action the learner completes. Only authors and tests read it.
- **`hint`** appears in a toast at the bottom of the interactive panel when the learner's input misses the item. The hint stays visible until the learner dismisses it or meets the requirement. It must start with `You can` or `You should`, or `curriculumIntegrity.test.ts` fails. An item without a hint never shows a toast, so give every board item one.
- **`test`** is graded by the panel's `LessonEngine` (`src/curriculum/lessonEngine.ts`). The placeholder panel ignores it.

A lesson with a `board` grades its checklist live after every value, candidate, or selection change. Give each item exactly one of these tests:

| Test                                   | Passes when                                                        |
| -------------------------------------- | ------------------------------------------------------------------ |
| `{ "selected": ["r1c1", "r1c2"] }`     | The selection is exactly these cells, in any order.                |
| `{ "values": { "r1c1": 5 } }`          | Each listed cell holds that value. Other cells don't matter.       |
| `{ "candidates": { "r1c1": [2, 5] } }` | Each listed cell has exactly these candidates. An extra one fails. |
| `{ "solved": true }`                   | Every cell matches `solution`.                                     |

### When hints show

Items are checked from the top of the list, and only the topmost unfinished item can show its hint:

- An input that misses that item shows its hint. For a `selected` test, a miss is a selection change that doesn't add a target cell. For the other tests, a miss is a board entry that doesn't fill or fix a listed cell.
- An input that moves toward the item shows nothing, so selecting the third of nine target cells stays quiet.
- A `selected` test ignores board entries, and the other tests ignore selection changes. Selecting a cell before typing into it never shows a hint.
- Meeting the item clears the hint. The next miss shows the hint of the item below it.

Lessons `102.md` (a `selected` test) and `103.md` (two `values` tests) show both patterns.

## Authoring a board

1. Decide what the learner practices, and keep the board and checklist to that goal.
2. Generate a puzzle. This prints a ready-to-paste `board` object with 1-based ids. `--seed` takes an integer and makes the output reproducible.

   ```bash
   pnpm lesson:board <variantId> [--seed n]
   ```

3. Paste it into the `# --config--` block. Trim `givens` for the lesson, and keep the full `solution`.
4. Write the checklist.
5. Check that the board is valid and has exactly one solution, equal to `solution`. A second valid solution would fail `{ "solved": true }` for a learner who found it.

   ```bash
   pnpm exec vitest run src/curriculum/curriculumIntegrity.test.ts
   ```

## Files block

`# --files--` seeds the interactive panel. Each `## <filename>` heading is followed by one code fence holding that file's contents:

````markdown
# --files--

## starter.txt

```txt
Replace this with the lesson's seed state.
```
````

## Author notes

`# --author-notes--` is free-form markdown for authors and reviewers. Record the lesson's goal and the decisions behind it. Learners never see it.

## Previewing and verifying

Copy `sample.env` to `.env` and set `SHOW_LEARN=true`. Set `SHOW_UPCOMING_LESSONS=true` too if you want to see WIP lessons. Then run `pnpm dev` and open `/learn`. The dev server rebuilds lesson data when a lesson file changes.

Before finishing, run:

```bash
pnpm build && pnpm test && pnpm lint
```

Lesson parsing errors fail both the build and `curriculumIntegrity.test.ts`. That covers unknown sections, a missing `alt`, disallowed HTML, and invalid config. `pnpm lint` runs Prettier over lesson files.
